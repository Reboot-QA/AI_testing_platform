# grill-with-docs（深度对话对齐）

> Spec 驱动工作流第 1 步：对齐 → `to-spec` → `implement-and-ship`。规则见 `.Codex/rules/spec-workflow.md`。
> 核心原则：**这一步不写代码、不出方案文件**，只把需求逼问清楚。宁可多问，不要假设。

## 触发后的行为

1. **不编码、不建文件**：只对话。若用户想直接开工，提醒「先对齐再出 Spec」。
2. **连环追问**，逐层逼出：
   - **核心目标**：这个需求到底要解决谁的什么问题？不做会怎样？
   - **范围边界**：明确「做什么」与「不做什么」，圈出本次范围。
   - **edge case**：空值 / 极值 / 并发 / 权限越界 / 失败回滚，逐项问预期行为。
   - **与现有模块的交互影响**（本仓库重点）：
     - apifox 分层（`routers/services/repositories/models/apifox`）是否需新增/改动？
     - 权限（部门 + 项目隔离 + 菜单权限）如何约束？
     - 涉及写操作的实体是否带乐观锁 version → 冲突 409 如何表现？
     - 是否触及 SSE 执行引擎（`services/apifox/run_engine`）？
     - 前端是否要新增类型（走 `pnpm gen:api-types`，不手写）？
   - **质疑设计**：对不合理/过度设计直接反问，给替代方案让用户选。
3. **一次问一组**，拿到答复再深入下一层；避免一次抛太多问题。

## 产出

- 一份**对齐要点清单**（目标 / 范围 / 边界与 edge case / 影响面 / 待定项），在对话中呈现。
- 结束语提示：「对齐完成，可以说『生成 spec』进入 `to-spec`」。

## 不做
- 不写代码、不建 Spec 文件、不发任何 glab 命令（那是后续技能的事）。
